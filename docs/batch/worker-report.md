# Worker report: paired orbit batch (2026-09-14)

Batch `report-2026-09-14` (`docs/batch/report-2026-09-14.md`) ran `tasks/orbit` three times at 27B, orchestrator pattern: the proven baseline config, the same config with the worker `report` tool on (gate reason `unreported` refuses `done` while a completed worker has no report), and that config plus `report.autoProbe` (the supervisor runs each report's verify cases as a probe when it lands). All three passed the oracle 48/48 on the first `done` claim.

Worker counts (from the batch report): 2 workers on the baseline, 3 on the report run, 1 on the report+auto-probe run. `E_excl` counts only fresh input + generated output; on raw tokens the baseline used ~424k, the report run ~234k, the report+auto-probe run ~611k.

**Did workers call `report` unprompted beyond the appended paragraph?** The paragraph appended to the worker prompt when reports are on (`lib/worker-def.mjs` `REPORT_INSTRUCTION`) says to call the tool "once" before the final message, and the tool's own description repeats "call it once at the end of your work." Neither run held to that. In the report run, worker `7702729a-c680-462` filed three back-to-back calls at t=863.9s, 895.4s and 910.8s, all "8 findings, 9 verify cases, 2 files" with identical content (`runs/2026-09-14T16-18-08/audit.jsonl`); the other two workers in that run called it once each. In the report+auto-probe run, the sole worker filed five times: the first two (t=621.9s, 674.3s) are identical "6 findings, 5 verify cases, 1 files," but the next three (t=1487.8s, 1572.3s, 1829.5s) carry genuinely new findings from further work the orchestrator asked for after the initial "done" (running and reporting on two scratch scripts, 0 verify cases each). So this run's repeats are not all duplicates of one report; only the first two are. Read together, the tool's return message ("Finish your turn with a short message; the orchestrator sees both") does not stop a worker from filing again once the orchestrator re-engages it in the same spawn — "once" seems to be read as "once per turn," not "once ever." This is a prompt-wording observation, not five (or three) distinct independent reports; the finding count that matters is 1 report call carrying the worker's actual account of the task, plus repeats.

**Did the gate ever fire, and what did the orchestrator do next?** No. `grep -c "approval without worker report" runs/<id>/audit.jsonl` returned 0 for both treatment runs, and `summary.reports.unreported` was `[]` at finish in both. Every worker had already filed a report by the time the orchestrator attempted `done` (`doneAttempts: 1` in every run, first attempt accepted), so the gate had nothing to refuse. This batch cannot say what the orchestrator does after a refusal — that needs a run where a worker actually finishes without reporting, which neither treatment run produced.

**Did auto-probe change the orchestrator's own probing?** `summary.reports.autoProbes` is 2 in the auto-probe run (the supervisor running the worker's own verify cases) and 0 elsewhere, and the orchestrator still probed before `done` in both treatment runs. The orchestrator's own probe traffic (`kind:"probe"`, `from:"orchestrator"` in `bus.jsonl`) was 5 messages carrying 53 cases in the report run and 5 messages carrying 58 cases in the auto-probe run (of 8 and 7 total probe events respectively, the difference being the 2 supervisor-run auto-probes in the latter that don't count as orchestrator messages) — so auto-probe did not reduce the orchestrator's own probe volume here; if anything it was marginally higher. In both runs, zero of the orchestrator's own probe cases matched any of the worker's verify-case argsets exactly (0 of 53, 0 of 58) — the orchestrator never reused what the worker had already verified, auto-probe or not, so on this pair auto-probe looks additive rather than substitutive for the orchestrator's own checking.

N=1 per arm. A second pair would settle whether the report run's speed (1318.8s, 234k tokens, the cheapest and fastest of the three) and the auto-probe run's cost (1971.9s, 611k tokens, on par with the no-report baseline despite running with a single worker) are the report tool's doing or noise: a same-config baseline from 2026-09-11 (`runs/2026-09-11T21-35-14`: SUCCESS, 1086s, 3 workers, 12 probes) shows wall-time variance on `tasks/orbit` at this footprint is large even without any report-tool change, so neither treatment's wall-time or token difference from the 2026-09-14 baseline supports a KPI-gain claim from this batch alone. A second pair would also let the "call it once" wording get fixed and re-tested, and would need to include a run that forces a worker to finish before reporting to actually exercise the `unreported` gate.
